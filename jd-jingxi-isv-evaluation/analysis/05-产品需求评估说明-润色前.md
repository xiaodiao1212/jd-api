# 京东京喜 ISV 产品需求评估说明

以《京东京喜-ISV-需求清单》为基础，逐项说明已有基础、需要补齐的能力，以及与京东协作的重点。

## 先看整体判断

**本项目有明确的产品基础，尤其是商品素材生成和商品信息优化。** Sico AI 生图侠已有商品图片、一键主图、一键详情页及批量素材处理能力；Sico AI 巡检侠已有商品信息诊断、优化和信息分提升方向的基础。这些能力可以用于本项目，再结合京喜的商品规则、使用场景和发布要求进行适配。

经营分析和经营操作需要补充专门的产品能力。例如，识别潜力商品需要经营数据和评价方法；选择活动需要资格、利润及冲突规则；调整广告需要效果数据、操作权限和预算限制。这些功能不能仅凭已有生图或巡检能力认定已经具备。

自动经营还需要把“发现问题、选择动作、获得授权、执行、检查结果”连接起来。我方成熟的线上软件服务基础可以承载产品入口和页面，但复杂任务排序、自动执行、持续监控及策略学习仍需单独建设或核实。

### 八个模块，一眼看清

| 模块 | 可以从哪里开始 | 最需要解决什么 |
|---|---|---|
| 商品经营 | 复用商品信息诊断与优化基础 | 完整发品、内容写入及经营数据。 |
| AI素材 | 复用主图、详情页和批量素材能力 | 京喜适配、线上替换、视频及效果测试。 |
| 比价与定价 | 开发成本测算和价格建议功能 | 可信的竞品价格、商家成本和费用规则。 |
| 流量增长 | 从标题、素材优化扩展到分析 | 分商品、分渠道的曝光与成交数据。 |
| 活动经营 | 结合招标方流程梳理各类活动 | 官方资格、冲突规则和报名方式。 |
| 广告经营 | 以已有公开操作资料开展对接确认 | 效果数据、投放策略及授权执行。 |
| 店铺及服务 | 利用订单、售后、客服等数据基础开发 | 平台考核规则、模板配置和会员运营动作。 |
| 经营自动化 | 在现有软件基础上建设任务系统 | 排序、授权、执行结果及持续效果检查。 |

### 阅读这份说明前，需要知道的几件事

- **“招标方已有流程”沿用原清单的“是否已有”。** “是”表示招标方已有对应工具流程，不代表我方已经实现，也不代表它已具备商家可直接使用的完整产品形态。“否”沿用原清单标记；经营自动化部分原文未说明。
- **已有产品基础和京东接口条件分别判断。** 有生成能力，还要确认结果如何发布；有接口资料，还要确认是否适用于京喜以及我方能否获准调用。目前没有已确认应用权限的资料。
- **下文所说“需要开发”或“需要确认”，均以当前资料为依据。** 未找到对应公开接口时，仍可能存在京东内部能力，需要双方进一步核实。
- 文中SKU指商品的具体可售规格；CTR指点击率，CVR指转化率，ROI指投入产出比，GMV指成交金额。涉及经营计算时，还需统一各指标的统计范围和计算方式。A/B测试指比较两套方案的效果。

|---|---|---|

| **一键发品**<br>自动生成标题、属性、卖点、图片、详情并创建商品 | 否 | 可复用图片和商品信息生成基础。仍需补齐内容组合、类目校验和创建流程，并确认标题、属性、图片、详情能否完整写入，以及何时算发布成功。 |
| **AI标题优化**<br>识别标题问题并生成推荐标题 | 是 | 可基于巡检侠的商品信息优化基础进行适配。重点是京喜标题规范和商品事实；生成推荐标题已有较清晰的实现路径，是否直接替换线上标题需另行确认。 |

| **商品属性补全**<br>自动识别并补齐缺失属性 | 否 | 可承接巡检侠的问题识别和优化基础。需要结合类目要求、商品资料补值；无法证明的属性应由商家补充，实际写入范围也需确认。 |

| **商品搬运**<br>支持多平台商品链接导入并完成商品创建 | 是 | 需要补充跨平台链接解析、字段转换和素材处理流程。已有能力可支持部分内容加工；来源资料的可用范围、使用依据，以及京东端的完整创建仍需明确。 |
| **潜力SKU识别**<br>识别值得重点投入经营资源的SKU | 否 | 需要新建商品评价方法，并取得本店销售、利润、库存等经营资料。行业热销信息只能作为参考，不能直接说明某个店内商品值得投入。 |
| **一品一策**<br>为重点SKU生成完整经营方案 | 否 | 需要把商品、价格、流量、活动和广告的资料汇总起来，再形成有依据的方案。商品信息经验可作参考，但跨模块经营方案仍需开发；原需求并未要求方案自动执行。 |

**与京东协作的重点：** 确认完整的商品创建与编辑能力、信息分规则和商机数据范围；经营推荐还需要明确可用的店内商品数据。

## 二、AI 素材能力

**这是现有能力最容易发挥作用的模块。** 主图和详情页生成有明确基础，套图与广告素材可在此基础上适配。视频生产、平台批量替换和素材效果测试，需要分别补充能力。

| 产品需求与原始目标 | 招标方已有流程 | 产品评估 |
|---|---|---|
| **AI主图生成**<br>根据商品信息生成主图 | 是 | 已有一键主图和商品生图能力，可复用核心生产能力。重点是适配京喜主图要求、准确表现商品；上传或替换线上主图需单独确认。 |
| **商品套图**<br>生成白底图、场景图、规格图、卖点图 | 是 | 可基于现有商品生图能力开发。四类图片各有不同表达要求，需要分别设计和验收，尤其要保证规格信息准确。 |
| **商详图生成**<br>自动生成详情图及详情结构 | 否 | 我方已有一键详情页能力，虽然招标方此项标记为“否”，仍可复用我方基础。需要适配京喜详情结构、内容规范和商品资料。 |
| **主图视频**<br>自动生成商品视频 | 否 | 需要新增视频生产能力。当前资料只证明已有图片和详情页能力，还不能证明已具备商品视频生成、画面连续性检查和视频审核流程。 |
| **批量素材处理**<br>支持多SKU批量生成及替换 | 是 | 批量生成与处理有明确基础。“替换”还需要对接每个商品的素材位置，并处理部分失败、重复操作和结果检查，交付范围应同时包含生成与替换。 |
| **主图A/B测试**<br>支持素材测试、效果跟踪及优胜方案选择 | 否 | 需要建设实验评价能力。资料中已有素材实验和分流相关功能，但各版本效果数据、有效样本要求及优胜方案的应用方式仍需确认。 |

**与京东协作的重点：** 明确素材规格与批量替换规则，并补齐实验效果、创意效果和正式应用优胜素材所需的信息。

## 三、比价与定价能力

**这个模块的首要前提是拿到可信的数据，并统一利润的计算方式。** 当前我方能力资料没有证明已有专门的比价、定价产品。平台建议价和价格竞争力信息可以辅助判断，但竞品实时价格、历史价格及商家实际成本仍需单独解决。

| 产品需求与原始目标 | 招标方已有流程 | 产品评估 |
|---|---|---|
| **同款识别**<br>识别站内外同款/相似商品 | 是 | 需要商品匹配能力和可使用的站内外商品资料。还要区分“完全同款”和“相似商品”；当前资料中未发现完整对应的公开接口，需确认数据来源与可用范围。 |
| **实时比价**<br>获取竞品实时价格及促销价格 | 是 | 主要依赖竞品价格数据。地区、人群和促销条件都可能影响到手价，需要先明确比较条件和更新频率，再确定产品能承诺的实时程度。 |
| **价格趋势**<br>展示竞品历史价格变化 | 是 | 需要可信的历史价格记录。应分别确认能否取得过去的数据，以及能否从今后开始持续积累，避免承诺资料中并不存在的历史回溯能力。 |
| **建议价格**<br>结合竞品、毛利、平台规则给出建议价 | 是 | 需要开发综合定价判断。平台建议价可以参考，但商家成本底线、竞品情况和活动规则仍要同时纳入；原需求是给出建议，不默认自动改价。 |
| **毛利测算**<br>计算活动、广告、补贴等情况下的实际利润 | 是 | 可以建设透明的成本与利润计算功能。实际利润还需要采购、履约、广告、补贴和退款费用完整对应；按商家输入测算的结果，应与真实结算利润分开说明。 |
| **ROI指导**<br>根据成本结构给出广告ROI底线 | 否 | 可从商家提供成本的计算工具做起。需要先统一广告收入、费用和利润的计算方式，再推导投放底线；缺失成本不能用猜测填补。 |
| **动态调价**<br>根据竞争环境变化持续给出调价策略 | 否 | 需要持续获取竞争变化，并结合成本底线生成策略。原文要求持续给出调价建议；如果进一步要求系统直接改价，还需单独明确授权、限制和操作能力。 |

**与京东协作的重点：** 确认站内同款与竞品价格数据、历史范围和费用规则；站外来源与商家自身成本，也需明确由哪方提供。

## 四、流量增长能力

**商品信息优化可以复用，流量判断需要新建分析能力。** 首先要区分商品在搜索、推荐和广告中的表现。现有广告数据只能说明广告部分，不能直接代表整个商品的流量和转化情况。

| 产品需求与原始目标 | 招标方已有流程 | 产品评估 |
|---|---|---|
| **CTR诊断**<br>识别曝光高但点击低的商品 | 否 | 需要取得商品曝光、点击和渠道数据，再定义什么情况属于“点击低”。当前有报表框架及部分广告数据，还需确认全商品、各渠道数据是否可用。 |
| **CVR诊断**<br>识别点击充足但转化不足的商品 | 否 | 需要把点击和成交对应到同一商品、渠道与观察时间。还要明确转化按下单还是支付计算，才能给出可信的诊断。 |
| **搜索优化**<br>优化关键词、标题、搜索首屏素材 | 否 | 标题和素材部分可复用现有能力。关键词与搜索效果分析需要补充数据和方法，尤其要取得搜索词表现及首屏素材的效果依据。 |
| **推荐流量机会**<br>识别高转化但推荐曝光不足SKU | 否 | 需要推荐渠道的商品曝光和转化明细。行业热度或全店销量无法直接判断推荐曝光是否不足，相关数据范围需京东确认。 |
| **潜力SKU**<br>识别值得放大的商品 | 否 | 需要评价商品增加流量后的机会，以及库存等供给条件能否承接。可与商品经营模块共享数据，但本项侧重“是否适合放大流量”，评价目标应分别保留。 |
| **流量放大策略**<br>输出搜索、推荐、广告等组合增量方案 | 否 | 需要开发跨渠道方案能力，结合预算、目标与各渠道表现给建议。方案可以作为商家决策依据，实际增量仍需后续验证。 |

**与京东协作的重点：** 提供具体到商品、渠道和时间的经营报表，并统一曝光、点击、成交及退款修正等计算方式。

## 五、活动经营能力

**活动规则和报名条件决定这一模块能做到什么。** 我方需要开发资格判断、活动推荐、收益测算和复盘功能；京东侧则需明确各类活动的数据、规则与操作方式。

原清单重点场景包括：**官方直降、首购礼金、秒杀、特价、便宜包邮、百补、顺手买、买赠、换购、焕新补贴。** 这些活动需要逐场景确认，不能按一套通用促销规则统一处理。

| 产品需求与原始目标 | 招标方已有流程 | 产品评估 |
|---|---|---|
| **活动资格识别**<br>判断商品可参加哪些活动 | 是 | 需要京东提供活动门槛、适用商品范围及当前资格判断依据。招标方已有流程可供后续对接，但其内部规则和调用权限目前未获提供。 |
| **最优活动推荐**<br>根据利润、库存、价格选择最适合活动 | 否 | 需要新建推荐方法，并同时考虑可参加资格、利润、库存和冲突条件。首先要明确商家更看重销量、利润还是其他目标。 |
| **活动收益测算**<br>测算活动预期GMV及利润 | 否 | 需要专门建设测算或预测能力。按假设计算收益可以说明情景；预测真实成交则需要历史样本，并说明结果的不确定性。 |
| **活动冲突判断**<br>判断价保、价格保护及其他活动冲突 | 是 | 重点依赖官方规则或平台校验结果。事后价保记录不能直接替代报名前的冲突检查，需确认活动叠加、价保及补贴限制。 |
| **一键提报**<br>支持直接报名或生成提报底表 | 是 | 原文允许两种交付方式。生成底表需要明确模板和校验规则；直接报名还需确认报名、审核和结果查询能力。底表生成完成不能记作报名成功。 |
| **活动复盘**<br>分析活动前后增量效果 | 否 | 需要活动关联的成交、费用和对比资料。可以分析活动前后变化；若要判断增长是否由活动带来，还需设计合适的对照，排除同期其他变化。 |

**与京东协作的重点：** 按上述活动逐一确认资格、价格与库存门槛、叠加规则、报名结果及费用承担；暂不支持直接报名的场景，明确底表方式是否满足要求。

## 六、广告经营能力

**资料中已有广告计划、预算调整和启停等相关能力，但产品接入条件尚需核实。** 我方需要建设选品、方案、调优和复盘逻辑；京东侧需要确认适用广告产品、调用方式及效果数据的计算规则。

| 产品需求与原始目标 | 招标方已有流程 | 产品评估 |
|---|---|---|
| **广告选品**<br>识别适合启动广告的SKU | 否 | 需要结合商品历史表现、毛利和库存评价投放机会。单看已有广告计划的结果，还不足以判断所有商品是否适合开始投放。 |
| **投放方案**<br>输出计划、预算、ROI目标及出价建议 | 否 | 需要新建方案生成与校验能力。预算、出价和投产目标应符合商家成本、账户条件及具体广告产品规则。 |
| **一键建计划**<br>支持自动创建广告计划 | 否 | 已有相关创建接口资料，可作为对接起点。仍需确认京喜适用范围、完整参数和权限，并分别检查计划创建成功、是否实际开始投放。 |
| **智能调优**<br>根据实时数据调整预算、出价、ROI | 否 | 需要专门的优化策略和执行控制。广告成交反馈可能延迟，过早调整容易误判；还要确认数据更新速度及各参数是否允许修改。 |
| **放量**<br>识别高ROI计划并扩大预算 | 否 | 需要开发扩量判断，并设定预算增幅与观察条件。当前表现好，不代表增加预算后仍保持同样效率；是否无人值守执行应由授权规则明确。 |
| **止损**<br>对低效计划及时降预算/暂停 | 否 | 可以围绕阈值、降预算和暂停建设产品。关键是避免将尚未回传的成交误判为低效，并确认停止或调整已经生效。 |
| **创意生成**<br>自动生成广告图片及卖点 | 否 | 可复用商品素材和信息生成基础，适配广告规格与表达即可形成开发方向。本项以生成图片和卖点为目标；原文没有要求必须先取得广告效果。 |
| **关键词优化**<br>增词、删词、强化高价值关键词 | 否 | 需要关键词级别的效果数据和增删操作。现有资料出现关键词相关字段，但尚不足以证明完整的优化操作，需京东进一步确认。 |
| **广告复盘**<br>分析GMV、ROI、消耗效率 | 否 | 需要开发统一的效果分析。现有资料包含曝光、点击及部分成交、费用字段，但成交归属、金额单位和统计时间仍需确认。 |

**与京东协作的重点：** 确认京喜可用广告产品、计划与关键词操作、预算限制，以及成交、费用和投产比的计算方式。自动调整还需明确商家授权范围。

## 七、店铺及服务能力

**订单、售后和客服数据提供了部分基础，店铺规则与实际操作方式仍需补齐。** 这些属于新的业务产品，不能因为已有通用软件基础，就认定已有完整服务能力。

| 产品需求与原始目标 | 招标方已有流程 | 产品评估 |
|---|---|---|
| **店铺升星助手**<br>计算距离下一星级的差距并生成最短提升路径 | 是 | 需要京东提供星级规则、当前指标和升级阈值，再开发差距分析。还需明确“最短”按什么衡量，才能比较不同提升路径。 |
| **客服诊断**<br>识别超时咨询、高频问题、排班空档 | 是 | 会话、聊天、等待时长和在线状态可作分析基础。排班空档还需要计划班表与实际工作记录，不能只看客服当前是否在线。 |
| **AI客服回复**<br>自动生成并配置回复模板 | 是 | 需要开发回复内容与模板管理。除生成话术外，还必须确认怎样保存、审核和启用客服模板；已有消息发送能力不能代替模板配置。 |
| **履约诊断**<br>分析揽收率、延迟发货、配送时效 | 是 | 订单时间和物流轨迹已有数据基础。产品仍需按京喜考核规则计算，明确哪些订单计入统计、何时算延迟，以及揽收和签收如何识别。 |
| **售后诊断**<br>自动读取售后原因并给出解决方案 | 否 | 当前资料已明确提供一级、二级售后原因，可用于开发诊断功能。解决建议还要结合售后政策和商家实际情况；权限与适用范围仍需确认。 |
| **售后沟通话术**<br>自动生成消费者沟通内容 | 否 | 可开发基于售后场景与规则的话术工具，由商家提供必要资料。重点是准确表达处理方案、避免虚构赔付承诺；自动发送不是原文明确要求。 |
| **店铺层级助手**<br>拆解距离下一经营层级的差距 | 是 | 依赖京东的经营层级规则和当前指标，需要据此开发差距拆解。经营层级与店铺星级应分别确认，不能直接共用一套规则。 |
| **店铺装修优化**<br>根据店铺流量及CVR优化页面结构 | 否 | 需要页面结构、访问路径和转化资料，再开发优化建议。还应明确交付是结构建议，还是由系统直接修改并发布装修页面。 |
| **会员运营**<br>会员招募、分层、权益及复购运营 | 否 | 会员资料、消费统计和部分权益功能已有接口基础。完整产品还要补齐招募、权益配置、触达及效果跟踪，并确认用户授权和适用会员体系。 |

**与京东协作的重点：** 明确星级与层级规则、客服模板配置、排班来源、履约及售后政策，以及会员招募与触达能力。

## 八、经营自动化能力

**这一模块需要作为独立产品能力建设。** 它要解决的核心问题是：多个任务同时出现时先做什么、哪些动作允许自动做、出错后如何处理，以及怎样判断做完是否有效。

| 产品需求与原始目标 | 招标方已有流程 | 产品评估 |
|---|---|---|
| **AI任务编排**<br>多条规则同时触发时进行优先级判断及任务排序 | 未说明 | 需要建设规则优先级、冲突处理和任务状态管理。可由我方实现编排；现有软件基础及京麦任务记录功能都不能证明这些能力已经具备。 |
| **AI自动执行**<br>获得授权后自动调用商品、价格、活动、广告工具 | 未说明 | 需要逐项接通实际业务动作，并设置授权范围、预算或价格限制、失败处理和人工暂停。任一类动作尚未开放时，就不能承诺全部经营操作自动完成。 |
| **自动复检**<br>任务执行后自动监控对应指标是否改善 | 未说明 | 需要把执行动作与后续指标对应起来。首先检查修改是否生效，再观察经营表现；观察多久、采用哪些指标，应按具体任务确定。 |
| **AI经营复盘**<br>自动生成经营日报/周报 | 未说明 | 需要整合各模块数据并开发周期报告。主要难点是数据完整、计算一致和更新及时，而不只是生成一段文字。 |
| **策略A/B实验**<br>对不同经营Solution进行实验验证 | 未说明 | 需要双方共同确定可测试的经营方案、对照分组和评价方法。已有素材实验能力只能覆盖部分场景，不能直接套用到全部经营策略。 |
| **策略学习**<br>基于历史Action→Result持续优化策略 | 未说明 | 需要长期记录“做了什么、结果怎样”，并验证策略调整是否有效。当前没有已具备该能力的事实，需专项建设，避免把同期自然变化误认为策略收益。 |
| **异常预警**<br>自动识别经营异常并触发任务 | 未说明 | 需要持续数据、异常判断、重复预警合并及任务触发机制。自动发现问题和创建任务，并不自动获得修改商品或花费预算的权限。 |

**与京东协作的重点：** 明确任务执行由谁负责、业务结果如何获取、数据更新能否满足监控需要，以及哪些实验需要平台配合。

在具体实现上，可以先约定“多久需要看到变化”，再判断采用定期查询还是平台主动通知，无需预先要求所有功能都实时推送。

## 双方接下来需要一起确认什么

为便于后续沟通，建议围绕以下事项收敛产品范围：

| 需要确认的事项 | 确认后能解决什么问题 |
|---|---|
| **商品内容规则与发布方式**：可修改哪些内容、需要哪些校验、如何确认生效 | 确定一键发品、属性补全、信息分优化及批量替换的完整交付范围。 |
| **经营数据范围**：具体商品、渠道、活动和页面能提供哪些指标，更新多快 | 确定潜力商品、流量诊断、经营复盘和执行后检查的可靠程度。 |
| **竞品、成本及费用来源**：同款与价格、商家成本、广告费用和补贴怎样取得与计算 | 明确比价、建议价格、毛利测算和投放底线的依据。 |
| **活动及广告操作**：哪些场景支持查询、报名、调整和停止 | 确定能直接执行的功能，以及需要商家确认或使用底表的场景。 |
| **店铺服务与会员规则**：星级、层级、客服、履约、售后和权益分别采用什么标准 | 避免产品计算与平台考核不一致，并明确可执行的服务动作。 |
| **授权、监控及实验责任**：哪些动作可以自动做、如何暂停、怎样判断有效 | 确定自动经营的安全边界和结果验收方式。 |

## 如何看待这份初步评估

本项目可以从已有商品素材与信息优化能力出发，扩展经营分析与操作产品。后续应把每项需求落实到可验收的结果：交付了什么内容、完成了什么操作、能看到什么效果，以及哪些条件需要京东提供。

当前最明确的是已有能力的复用方向；需要继续确认的是经营数据、业务规则、实际操作和授权范围。待这些条件明确后，双方即可进一步确定每项产品的完整交付内容。
