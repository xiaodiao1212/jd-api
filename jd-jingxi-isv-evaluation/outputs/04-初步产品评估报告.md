# 京东京喜 ISV 产品初步评估报告

评估日期：2026年9月13日。范围为提供的需求清单、现有能力事实基线与本地京东开放平台资料。本报告不包含工期、精确成本或上线日期评估，未进行线上接口调用与应用授权验证。

## 一、项目理解

本项目希望把商品、素材、价格、流量、活动、广告和店铺服务连接为可使用、可执行、可复检的经营产品。核心价值既包括提高内容生产和日常分析效率，也包括帮助商家做出有依据的经营选择，并在明确授权后执行部分操作。

需求清单共60项，分为8个模块。其中20项标记招标方已有CLI流程、33项标记否，经营自动化7项未说明。这些流程可以作为后续业务规则和交互设计的参考，但不能据此认定已经SaaS化、已有公开接口或具备生产级自动执行能力。我方能力应单独按事实基线评估。

产品验收需分别明确四类结果：生成了可用内容或建议、平台接受了操作、业务状态实际生效、经营指标出现改善。这四类结果对应不同证据，不能用“执行成功”替代“效果提升”。依据为R002、R014、R039–R041及R054–R060，逐项证据见附件矩阵。

## 二、总体评估结论

**本项目具备分层产品化基础，但不能将60项需求整体视为现有工具的直接包装。** 最明确的复用入口是商品主图、详情页及批量素材生成，以及商品信息巡检优化。需要专项建设的部分主要集中在经营评分、跨数据分析、视频生产、自动化执行和策略实验；平台侧约束主要集中在指标口径、竞品数据、活动规则、动作合同与应用权限。

建议按能力成熟度确定产品边界：先确认能稳定交付的内容与诊断产物；对商品创建、素材替换、广告动作等功能逐项确认操作合同与生效结果；对经营自动化与学习能力，以可观察、可暂停、可归因的具体场景完成联合定义。这是范围与验收顺序的建议，不是实施排期。

采用五类产品判断：A为可直接产品化；B为基于已有能力二开；C为专项研发；D为强依赖京东数据或接口；E为需要双方联合定义或研发协同。每项只计一个主要标签，辅助标签保留其他重要依赖，不能将下表解释为互不相关的研发项目数量。

| 主要产品标签 | 需求数 |
|---|---|
| A | 2 |
| B | 10 |
| C | 32 |
| D | 14 |
| E | 2 |


A类判断仅适用于明确的核心交付边界，例如商家提供商品资料后生成主图或详情页，并不包含未经验证的平台上传、替换与发布。B类仍需要场景适配和验收，不能等同于需求已经完成。

## 六、需要京东侧协同的能力

接口协同应优先回答明确的数据或动作合同，避免各模块分别提出“是否有接口”的泛化问题。本次已归并为18项可回填问题，重点包括：

1. **接入与数据基础**：京喜商家适用模式、应用权限；商机版本；按SKU、渠道、活动和页面划分的具体报表；竞品同款及实时/历史到手价；费用和补贴口径（Q01、Q04–Q07）。
2. **业务操作与规则**：完整商品写入及价格动作；信息分和内容标准；十类重点活动的资格、叠加、报名及审核；广告产品及关键词操作合同；素材替换和实验结果（Q02、Q03、Q08–Q10）。
3. **服务与会员场景**：客服排班与模板配置；履约考核及售后政策；星级与经营层级；店铺页面边界；会员招募、权益和触达（Q11–Q16）。
4. **经营闭环**：任务调度责任、事件与回执，以及跨策略实验控制和结果归因（Q17、Q18）。

其中，活动经营必须按官方直降、首购礼金、秒杀、特价、便宜包邮、百补、顺手买、买赠、换购和焕新补贴分别确认适用合同。当前资料中的活动上报接口不能替代这些场景的资格和报名接口。若某场景只支持底表，应明确底表模板与校验规则，并将其与线上直接报名分别验收。

新增接口只是待确认的一种可能结果。若京东已有适用内部能力，优先确定开放范围；若现有公开接口已覆盖，则补齐权限、规范定义和样例即可，不能未经确认就认定需要新增研发。

## 七、重点研发与探索能力

**经营评分和排序。** 潜力SKU、广告选品、活动推荐与流量方案需要明确定义优化目标，组合流量、利润、库存和可执行条件。重点是指标可靠性和解释能力，不应仅根据现有销量排序。商品经营潜力SKU与流量潜力SKU可共享事实数据，但须保留不同评价目标（R008、R028、R031、R036）。

**预测和动态优化。** 活动预期GMV及实时广告调优需要样本、约束和反馈窗口，属于专项探索。应区分情景测算与预测：前者说明输入假设，后者需要验证误差和不确定性；不能将一次建议包装为稳定增益能力（R032、R039）。

**素材效果与策略实验。** 主图A/B测试需要各版本可比较指标与选优规则。经营策略实验进一步涉及实验单元、对照、跨工具干扰及因果归因，不能直接复用素材实验合同来覆盖所有经营方案。策略学习需要持续稳定的Action与Result记录，并验证新策略是否改善，而非仅累计历史记录（R015、R058、R059）。

**视频与服务产品。** 视频生产尚无既有能力事实，应单独建设。客服、履约、售后及会员产品虽然部分输入接口明确，仍需要专用规则、交互和验收，不能仅因有通用SaaS基础就视为直接复用（R013、R045–R053）。

## 八、经营自动化总体架构判断

建议将经营自动化设计为受控反馈链：**数据输入 → 诊断与建议 → 任务排序 → 商家确认或授权策略 → 业务动作 → 生效核验 → 指标观察 → 复盘与策略更新。** 各层可按明确场景独立验收，不要求所有功能一开始即进入无人值守模式。

|环节|我方产品责任|京东侧需确认的边界|
|---|---|---|
|诊断与编排|规则配置、目标约束、任务优先级与冲突处理|指标、业务约束、必要状态及数据更新方式|
|授权执行|按授权范围调用工具、控制额度、避免重复动作、保留操作记录与人工暂停入口|各动作权限、参数限制、幂等与生效回执；任务同步是否由京麦承载|
|复检与复盘|区分调用成功、业务生效与指标变化，形成可解释报告|状态查询、结果窗口、归因及刷新延迟|
|实验与学习|方案版本、实验评价、策略更新与退回依据|可控实验单元、结果数据与平台侧分流或执行能力|

成熟SaaS基座可以承载产品入口，但上述复杂编排、授权执行和学习机制未被既有事实证明，需单独建设或核实。京麦任务API可以成为状态同步的候选方式，不能据此把执行责任归给平台。

Callback不是所有产品的默认硬依赖。可满足业务时效的轮询同样可能可行；双方应先约定观察时效与配额，再决定哪些场景必须事件推送。R023的动态调价原文只要求持续策略；自动改价由R055在授权动作范围中独立定义。自动复检也不自动意味着允许继续执行后续经营动作。

## 九、风险与待确认事项

**合同完整性风险。** 当前资料中存在字段展开不足、部分中文说明乱码及广告方法标记非标准的问题。这些问题影响直接对接判断，应取得规范定义与样例响应；不能据此断言线上能力不存在（P01、P03、P05）。

**经营口径风险。** 广告成交不等于全店成交、市场商机不等于本店SKU潜力、物流轨迹不等于考核指标。具体报表、费用、归因和业务规则决定分析能否可信，必须作为验收输入（Q04–Q09、Q13）。

**授权执行风险。** 公开接口存在与当前应用获准调用是两件事；扩大预算、止损、改价及报名还需要明确授权范围、动作限制和异常控制。未确认接口或权限的路径应保留商家审核或明确缩小交付边界，不承诺完整自动化（Q01、Q02、Q08、Q09、Q17）。

**效果承诺风险。** 内容生成、诊断建议和平台执行都有可独立验收的产物；经营增长、预期收益和持续学习则需要结果数据及验证方法。报告不把研发可行性等同于商业效果保证（R015、R032、R035、R058、R059）。

## 十、结论

建议推进该项目，并以明确的产品交付边界和证据条件组织合作。商品素材与信息优化具备较清晰的复用基础，可以作为产品入口；经营分析和执行工具按数据、规则与动作合同逐项完成可行性确认；跨模块自动化和策略学习作为独立能力建设，并由双方共同定义实验、归因与授权责任。

下一步最有价值的工作，是由京东侧回填18项协同问题并提供关键接口合同、报表样例和业务规则，再据此收敛各产品的最终验收范围。现阶段足以区分复用、二开、专项研发和平台依赖，但不足以将全部需求承诺为已具备完整自动经营闭环。
